# ASN.1 document library requirements

This Python library reads, creates and modifies ASN.1 data and the cryptographic documents that use it. References to cryptographic-document standards identify their ASN.1 structures and field meanings; they do not claim cryptographic verification or validation of cross-field protocol policies.

### FP-01: BER and DER element framing

- Given a complete ASN.1 BER or DER element, expose its ASN.1 class, primitive or constructed form, tag number, encoded header, contents and terminator, and the total number of bytes occupied by that element. Interpret framing according to ITU-T X.690 (2015).

- By default, read the first element even if more bytes follow it. When complete consumption is requested, refuse trailing bytes as extra data.

- Refuse empty input, truncated identifiers, truncated lengths, contents shorter than their declared length, missing indefinite-length terminators, indefinite lengths on primitive elements and nonminimal tag encodings as malformed ASN.1. Refuse non-binary input as an input-type error.

- For an indefinite-length outer element whose nested containers also use indefinite lengths, support at most ten enclosing elements above any descendant, counting the outer element and excluding the descendant itself. Refuse deeper such nesting as excessively nested ASN.1.

- Given an ASN.1 class, primitive or constructed form, nonnegative tag number and binary contents, produce the definite-length element framing required by ITU-T X.690 (2015) DER for those inputs. Accept universal, application, context-specific and private classes; refuse other classes, other forms and negative tags as invalid values, and refuse inputs of incompatible types as input-type errors.

### FP-02: ASN.1 values and native interpretation

- Read, create and serialize ASN.1 boolean, integer, enumerated, null, object identifier, bit string and octet string values, preserving their meanings under ITU-T X.690 (2015). Newly created values use DER. Refuse a requested ASN.1 type whose tag or primitive or constructed form is incompatible with the supplied encoding as a type mismatch.

- Support caller-defined names for integer values, enumerated alternatives, object identifiers and bit positions. Preserve unmapped integers and object identifiers numerically; restrict enumerated values to their declared alternatives. Permit individual named bits to be read and changed, and expose the set of enabled names. Refuse undeclared enumeration values and unknown supplied integer or object-identifier names as invalid values. Refuse named-bit lookup or assignment through an undeclared name as an invalid bit selection. Accept positional bit sequences containing only zero and one. For a named-bit definition, refuse a positional sequence extending beyond its highest declared bit position as too many bits.

- Expose object identifiers both by their caller-defined names and by their dotted numeric identities, and translate between a declared name and its numeric identity. Refuse object identifiers whose first arc is greater than two or whose second arc exceeds 39 when the first arc is zero or one as invalid identifiers.

- Read and create UTF-8, Numeric, Printable, IA5, Graphic, Visible, General, Universal, Character and BMP ASN.1 text strings, preserving text through serialization and decoding. Use UTF-8 for UTF-8 strings, UTF-32 big endian for Universal strings, UTF-16 big endian for BMP strings and ASCII for IA5 strings. Numeric, Printable, Graphic, Visible, General and Character strings accept ISO-8859-1 characters without enforcing their narrower ASN.1 alphabets. Preserve Teletex strings containing ASCII letters, ASCII digits and spaces through text conversion and serialization. Treat Videotex strings as binary values. Refuse text that cannot be represented in the selected encoding as an encoding failure.

- Interpret bit strings as bits, binary octets or nonnegative integers, and octet strings as binary octets or nonnegative integers, according to the caller's chosen interpretation. Preserve the underlying ASN.1 contents when changing between interpretations with the same ASN.1 tag; refuse conversions between different tags as incompatible conversions. A caller-selected integer octet width retains leading zero octets when the value fits that width.

- Decode constructed indefinite-length octet strings, bit strings, binary Videotex strings and text strings into their complete logical values, including nested chunks. When canonical serialization is requested, produce the corresponding primitive DER value under ITU-T X.690 (2015).

### FP-03: Structured ASN.1 documents and custom definitions

- Given a caller-defined ASN.1 document definition, read and create records, homogeneous collections and alternatives, including definitions that refer to themselves. Expose record fields by their declared names, ordered collection members in their supplied order and the identity and value of the selected alternative. Support ordered records, unordered records, ordered collections and unordered collections; accept unordered record fields in any encoded order.

- Honor optional fields and caller-declared defaults. An omitted optional field is observably absent and contributes no encoded value; an omitted defaulted field exposes its declared default. Removing a defaulted field restores that default. Refuse serialization of a newly created record missing a mandatory field as an incomplete document. Refuse interpretation of an encoded record lacking a mandatory field as an incomplete document. Refuse a value whose tag cannot satisfy a required typed field or any declared alternative as a document-type mismatch.

- Allow callers to assign and replace fields, append and replace collection members, and remove optional fields or collection members. A subsequent serialization includes changes to nested values even after earlier serializations. Independently copied documents initially retain the same values. Subsequent changes to either document remain independent and are observable through individual nested fields and subsequent serialization.

- Apply caller-declared explicit and implicit ASN.1 tagging in universal, application, context-specific and private classes according to ITU-T X.690 (2015), using the supplied definition and values. When assigning a value to a field, the field declaration takes precedence over tagging attached to the supplied value. A tag supplied without a class uses the context-specific class. Support nested explicit tags. Allow a tagged value to be copied with different tagging or with special tagging removed while preserving its interpreted value; refuse implicit tagging of an alternative selection as an unsupported tagging request.

- Accept open ASN.1 values and ASN.1 documents embedded in octet strings or bit strings. Interpret them using a caller-supplied definition or a caller-declared association between an object identifier and a definition. Preserve the encoded open value when no association is declared; refuse interpretation against an incompatible supplied definition as a document-type mismatch.

- Serialize newly created structured values and explicitly requested canonical output as DER under ITU-T X.690 (2015), using the document definition, field values, defaults and tagging supplied by the caller. For loaded unordered records, canonical serialization is supported after their fields have been interpreted. Ordinary serialization of an unchanged definite-length document preserves its original encoding, including BER encodings within it.

- Read and create concatenations of caller-declared ASN.1 documents, keeping each component independently accessible. Refuse trailing bytes beyond the declared components when complete consumption is requested as extra data.

- For a supplied ASN.1 value, provide a diagnostic view that distinguishes its nesting, ASN.1 tags and tagging, encoded data and interpreted values. Nested fields and embedded interpreted documents remain distinguishable from their enclosing values.

- Read supported universal ASN.1 values without a caller-supplied document definition, identifying their types from their universal tags. For sequences without declared fields, expose their members by position in encoded order, including nested sequences. For sets without declared fields, identify the universal set type and preserve its encoded form.

### FP-04: ASN.1 times and extended dates

- Read ASN.1 UTC time with a two-digit year, month, day, hour and minute, optional seconds, and either UTC or an hour-and-minute offset. Interpret years 50 through 99 as 1950 through 1999 and years zero through 49 as 2000 through 2049. Missing seconds mean zero; return the represented date, time and offset. Refuse text outside this grammar or invalid calendar values as invalid time data.

- Read ASN.1 generalized time with a four-digit year, month, day and hour, optional minutes and seconds, an optional decimal fraction of the least precise supplied time unit, and an optional UTC or signed offset in hours or hours and minutes. Accept a dot or comma for the decimal fraction. Return the represented offset and a date and time within half a microsecond of the encoded instant; leave a time without an offset observably timezone-free. Refuse text outside this grammar or invalid calendar values as invalid time data.

- Create UTC time and generalized time from timezone-aware date and time values. Serialize them as DER under ITU-T X.690 (2015) after conversion to UTC; UTC time discards the subsecond fraction and generalized time preserves microseconds. Refuse timezone-free date and time inputs as missing timezone information, and refuse creation of UTC time outside 1950 through 2049 after conversion to UTC as an out-of-range time.

- Represent valid generalized dates and times in year zero as well as years one through 9999, using the proleptic Gregorian calendar. Permit inspection of calendar components, formatting, replacement of calendar components, comparison and time arithmetic across the year-zero boundary. Refuse invalid calendar component combinations as invalid dates.

### FP-05: PEM transport

- Detect the presence of a PEM opening boundary in binary input, distinguishing PEM-bearing input from input without such a boundary. Detection does not assert that a complete decodable block exists. Refuse non-binary input as an input-type error.

- Decode complete PEM blocks into their block identity, supplied header information and original binary payload. By default return the first block; when all blocks are requested, return them in input order. Accept surrounding non-PEM text and both ordinary and spaced PEM boundary conventions. Header values exclude leading and trailing spacing. Refuse input containing no completed block as malformed PEM, and refuse non-binary input as an input-type error.

- Encode a supplied binary payload, block identity formed from uppercase ASCII letters, digits and spaces, and optional single-line ASCII headers as PEM. Refuse a non-binary payload or a non-text block identity as an input-type error, and a block identity whose uppercase form contains non-ASCII characters or non-ASCII header text as an encoding failure.

### FP-06: Cryptographic algorithm descriptions and signature conversion

- Read, create and modify algorithm descriptions that retain an object identifier and its parameters. Recognize digest descriptions for MD2, MD5, SHA-1, SHA-224, SHA-256, SHA-384, SHA-512, SHA-512 with 224-bit or 256-bit output, SHA3-224, SHA3-256, SHA3-384, SHA3-512, SHAKE128 and SHAKE256, including the SHAKE forms with an explicit output length. Recognize HMAC descriptions for the SHA-1, SHA-2 and SHA-3 variants just listed, excluding SHAKE, and DES MAC. Preserve unrecognized algorithm identifiers and their supplied parameter values.

- For signature descriptions, distinguish RSA PKCS#1 v1.5, RSA-PSS, DSA, ECDSA, Ed25519 and Ed448. Recognize MD2 and MD5 with RSA, SHA-1 with RSA, DSA or ECDSA, and each of SHA-224, SHA-256, SHA-384, SHA-512, SHA3-224, SHA3-256, SHA3-384 and SHA3-512 with RSA, DSA or ECDSA. Include plain ECDSA descriptions for the same SHA families. Expose the signature family and the digest selected by a combined identifier or RSA-PSS parameters. Refuse digest lookup for an identifier that specifies no digest, including Ed25519 and Ed448, as unavailable algorithm information. CMS digest selection uses the same digest for combined identifiers and RSA-PSS, selects SHA-512 for Ed25519 and SHAKE256 for Ed448, and refuses other identifiers that specify no digest as unavailable algorithm information.

- Read and create RSA-PSS and RSA-OAEP parameter descriptions under RFC 4055, using the supplied digest, mask generation, salt-length, trailer and source parameters as applicable. Within supplied RSA-PSS and RSA-OAEP parameter descriptions, omitted digest and mask-generation choices select SHA-1 and MGF1 with SHA-1; omitted RSA-PSS salt length means 20 bytes and its omitted trailer selects the RFC 4055 trailer. An omitted RSA-OAEP source uses an empty label. Supply null parameters when omitted from newly created descriptions for the general RSA identifier, SHA-224, SHA-256, SHA-384 or SHA-512 with RSA, and the SHA-1, SHA-224, SHA-256, SHA-384 or SHA-512 digest identifiers.

- Read and create encryption descriptions for DES, three-key TripleDES, RC2, RC4, RC5, RSA PKCS#1 v1.5, RSA-OAEP and AES with 128-, 192- or 256-bit keys. Recognize AES ECB, CBC, OFB, CFB, key wrap, GCM, CCM and padded key wrap modes. Interpret structured parameters for DES, TripleDES, RC2, RC5, AES CBC, AES OFB, AES CCM and RSA-OAEP; preserve other supplied parameters as open values. For CCM parameters with an explicitly supplied nonce and authentication-tag length, retain both values under RFC 5084. For DES, TripleDES, RC2 and RC5 descriptions expose CBC mode; for AES descriptions expose the mode selected by the identifier. Expose each of these ciphers' identities and an initialization vector for DES, TripleDES, RC2, RC5, AES CBC and AES OFB when stored in their parameters. Expose AES block size as 16 bytes, DES, TripleDES and RC2 block size as eight bytes, and RC5 block size in bytes corresponding to its declared bit count. Expose AES key lengths as 16, 24 or 32 bytes according to the identified variant, DES as eight bytes and three-key TripleDES as 24 bytes. For RC2 parameter versions specifying 40-, 64- or 128-bit effective keys, expose the corresponding key length in bytes under PKCS#5 v2.1.

- Read and create PBES1, PBES2, PBMAC1, PBKDF2 and scrypt parameter descriptions under PKCS#5 v2.1 and RFC 7914, and Diffie-Hellman parameters under PKCS#3 v1.4, preserving supplied salts, counts, key lengths, algorithm choices and domain values. Support PBES1 combinations of MD2, MD5 or SHA-1 with DES or RC2, and PKCS#12 SHA-1 password-based descriptions for RC4 with 40- or 128-bit keys, RC2 with 40- or 128-bit keys, and two-key or three-key TripleDES under RFC 7292. An omitted PBKDF2 pseudorandom function selects HMAC-SHA-1. For PBES2 with PBKDF2, expose the embedded salt, iteration count, pseudorandom function, cipher and key length; an explicitly supplied derivation key length takes precedence over the cipher's key length. Refuse a request for the concrete salt when PBKDF2 declares an external salt source as unavailable parameter information. Expose scrypt's salt and cost, block-size, parallelization and optional key-length parameters as supplied values.

- Convert a two-integer DSA or ECDSA signature between its ASN.1 representation under RFC 3279 and its equal-width integer-pair representation under IEEE 1363-2000, preserving the two supplied nonnegative integers and their order. By default the output width of each integer is the minimum positive whole-byte width sufficient for the larger integer; accept a caller-specified larger width and refuse an insufficient width as too small.

- For the supported PBES1 descriptions, expose PBKDF1 as the derivation family, the identified digest, the supplied salt and iteration count, CBC mode, an eight-byte key and an eight-byte block. For the supported PKCS#12 password-based descriptions, expose PKCS#12 derivation with SHA-1 and the supplied salt and iteration count. Their key lengths are five or 16 bytes for the 40- or 128-bit RC4 and RC2 variants, 16 bytes for two-key TripleDES and 24 bytes for three-key TripleDES; RC2 and TripleDES use eight-byte blocks and CBC mode. For PBES2, expose the declared derivation family and the embedded cipher's block size, mode and stored initialization vector. When neither PBES1 nor a PKCS#12 password-based description stores an initialization vector, expose its absence.

### FP-07: Private and public key documents

- Read, create and modify RSA private and public key documents under PKCS#1 v2.1, DSA private key documents in the OpenSSL form, EC private key documents under SECG SEC1 v2, PKCS#8 private and encrypted-private-key documents under RFC 5208, and subject public-key information under RFC 5280. Preserve each supplied key component, algorithm parameters, optional attributes and encrypted payload. Recognize RSA-PSS key restrictions under RFC 4055 and Ed25519, Ed448, X25519 and X448 key payloads under RFC 8410. Subject public-key information additionally supports RSA-OAEP and Diffie-Hellman descriptions.

- Wrap standalone RSA, DSA and EC private keys in PKCS#8 without changing the supplied key material; preserve DSA domain parameters and EC domain parameters in the resulting document. Wrap standalone RSA public keys in subject public-key information. Wrapping leaves the supplied standalone document unchanged.

- Expose an EC key's domain declaration as a named curve, explicitly supplied domain parameters or parameters inherited from the issuing authority. Refuse curve-information requests for non-EC keys as incompatible key requests. For an explicit domain, expose the minimum whole-byte private-scalar width that accommodates every nonnegative scalar less than its supplied subgroup order within the following scope: orders from two through 2³², and larger orders of at most 1,024 bits whose distance from every power of 256 exceeds one trillionth of that power. Permit callers to register additional curve names, numeric identities and private-key byte widths; EC private keys subsequently created with that domain use the registered width. Refuse width lookup for a named curve without a registered byte width or for inherited domain parameters as unavailable curve information.

- Recognize the following built-in named curves. For newly created keys whose nonnegative private scalar fits the indicated width, use that private-scalar width in bytes, retaining leading zero octets and applying the width whether the domain is declared in the standalone key or its PKCS#8 container: 14 bytes for secp112r1 and secp112r2; 15 for sect113r1 and sect113r2; 16 for secp128r1 and secp128r2; 17 for sect131r1 and sect131r2; 20 for brainpoolp160r1 and brainpoolp160t1; 21 for c2pnb163v1, c2pnb163v2, c2pnb163v3, c2pnb176w1, sect163k1, sect163r1, secp160r1, secp160k1, sect163r2 and secp160r2; 24 for c2tnb191v1, c2tnb191v2, c2tnb191v3, c2onb191v4, c2onb191v5, prime192v2, prime192v3, secp192r1, secp192k1, brainpoolp192r1 and brainpoolp192t1; 25 for c2pnb208w1, sect193r1 and sect193r2; 28 for secp224r1, brainpoolp224r1 and brainpoolp224t1; 29 for sect233k1 and secp224k1; 30 for c2tnb239v1, c2tnb239v2, c2tnb239v3, c2onb239v4, c2onb239v5, prime239v1, prime239v2, prime239v3, sect239k1 and sect233r1; 32 for secp256r1, secp256k1, brainpoolp256r1 and brainpoolp256t1; 33 for c2pnb272w1; 36 for sect283k1 and sect283r1; 37 for c2pnb304w1; 40 for brainpoolp320r1 and brainpoolp320t1; 45 for c2tnb359v1 and c2pnb368w1; 48 for secp384r1, brainpoolp384r1 and brainpoolp384t1; 51 for sect409k1; 52 for sect409r1; 53 for c2tnb431r1; 64 for brainpoolp512r1 and brainpoolp512t1; 66 for secp521r1; and 72 for sect571k1 and sect571r1. Preserve each curve's numeric identity. For subsequently created keys, a caller-registered width supersedes the built-in width for that identity.

- Convert an uncompressed EC public point to its two integer coordinates, retaining coordinate order and values under SECG SEC1 v2. Refuse coordinate extraction from compressed points as unsupported point representation, and from an unrecognized point form as invalid key data.

- Identify key algorithms from their documents. RSA and DSA key-size inspection supports positive measured integers other than powers of 256; above 2³², the measured integer must differ from every power of 256 by more than one trillionth of that power. For RSA and DSA public keys with domain parameters, expose the key size in bits rounded up to a whole byte and its corresponding byte count, measured from the RSA modulus or DSA domain prime. For uncompressed EC public keys, expose the coordinate width in bits and bytes. For a document unchanged since its first digest request, compute SHA-1 and SHA-256 public-key digests under FIPS PUB 180-4 over the binary public-key payload, excluding the surrounding subject public-key information and the bit-string unused-bit count.

- For PKCS#8 RSA and DSA private keys, expose the key size measured from the RSA modulus or DSA domain prime in bits rounded up to a whole byte, and its corresponding byte count. For DSA domain parameters, expose the minimum unsigned whole-byte width of the positive subgroup order, excluding an ASN.1 sign-padding octet. For DSA public and private keys with supplied domain parameters and a subgroup order of 160, 224 or 256 bits, classify the digest family as SHA-1 for 160 bits and SHA-2 for 224 or 256 bits. Without DSA public-key domain parameters, expose the digest family as unavailable; refuse digest-family requests for non-DSA keys as incompatible key requests.

### FP-08: X.509 names and addresses

- Read, create and modify X.509 distinguished names under RFC 5280, preserving relative distinguished-name grouping, attribute identities, repeated attributes and their text or binary values. Retain multiple values of a repeated attribute in the native representation instead of overwriting them.

- Build distinguished names from supplied attributes, emitting one relative distinguished name per attribute in this order: incorporation country, incorporation state or province, incorporation locality, business category, serial number, country, postal code, state or province, locality, street address, organization, organizational unit, title, common name, user identifier, initials, generation qualifier, surname, given name, name, pseudonym, distinguished-name qualifier, telephone number, email address, domain component, name distinguisher, organization identifier, TPM manufacturer, TPM model, TPM version, platform manufacturer, platform model, platform version and unique identifier. Accept their numeric attribute identities as well as their registered names. Refuse an attribute with no known value interpretation as an unsupported attribute. Directory-string attributes use UTF-8 by default or caller-selected Printable text, while country, serial number and distinguished-name qualifier always use Printable text.

- For distinguished names with no repeated attribute identity within a relative distinguished name, compare the supplied attribute identities, values and grouping using RFC 5280 section 7.1 and RFC 4518 string preparation. Refuse comparison of directory text prohibited by RFC 4518 or containing a malformed bidirectional sequence as invalid directory text.

- Read and create the RFC 5280 general-name alternatives: other name, email address, DNS name, X.400 address, directory name, URI with a DNS-named authority, IP address and registered identifier. Preserve the chosen alternative and its value. For an EDI party name supplied in encoded form, identify its alternative and preserve its encoding. For international DNS and email domains, preserve domain identity through conversion between Unicode text and serialized IDNA representations under RFC 3490. Compare email addresses with case-sensitive local parts and case-insensitive domains. Support IPv4 and IPv6 addresses and address ranges with prefix lengths of zero through 32 for IPv4 and zero through 128 for IPv6, refusing invalid addresses or out-of-range prefix lengths as invalid address data.

- Convert international URIs with DNS-named authorities between their Unicode and ASCII representations, preserving their scheme, authority, port, path, query and fragment. Use RFC 3986 and RFC 3987 for URI components and UTF-8 percent encoding, and RFC 3490 for international hostnames. Ordinary conversion retains an explicitly supplied default port; normalization removes port 80 for HTTP and port 443 for HTTPS. Refuse input of the wrong text or binary type as an input-type error.

- Decode Teletex directory strings as Windows-1252 by default for compatibility with existing certificates. A caller-selected strict interpretation uses the single-octet character assignments of ITU-T T.61 (1992), refusing unassigned octets as invalid text; after the selected strict scope ends, default decoding is restored.

- For a document unchanged since its first digest request, compute SHA-1 and SHA-256 digests under FIPS PUB 180-4 over the complete serialized name, including its ASN.1 framing. For names in which each binary-valued attribute identity occurs at most once, provide a readable name view containing each attribute identity and each supplied value, including repeated textual values.

- Compare ASCII DNS names without regard to letter case; compare decoded international DNS names by their decoded text without regard to case. Compare IP address values by address family, binary address and, for ranges, mask. Supported general-name alternatives with different identities compare unequal; alternatives with the same identity use their value comparison, with registered identifiers compared numerically and directory names compared by the distinguished-name rules. If either general name is an other-name, X.400-address or EDI-party-name alternative, refuse comparison as unsupported even when their alternative identities differ.

- For HTTP and HTTPS URIs with DNS-named authorities, compare otherwise identical values as equal when they differ only in scheme or hostname letter case, Unicode versus IDNA hostname representation, an explicit default port versus its omission, or percent encoding of unreserved characters under RFC 3986. With no query or fragment, an empty path and the root path compare equal. A change in path letter case or replacement of a literal path separator by a percent-encoded separator distinguishes otherwise identical URI values.

### FP-09: X.509 certificate inspection and construction

- Read, create and modify version-one, version-two and version-three X.509 certificate structures under RFC 5280 from supplied certificate fields, public key, algorithm descriptions and signature bytes. Expose issuer, subject, serial number, validity endpoints, public key, signature and algorithms, preserving the supplied document values. Preserve optional issuer and subject unique identifiers and extensions. An omitted certificate version identifies version one.

- Interpret certificate extensions for subject directory attributes, subject key identifier, key usage, private-key usage period, subject and issuer alternative names, basic constraints, name constraints, CRL distribution points, certificate policies, policy mappings, authority key identifier, policy constraints, freshest CRL, inhibit any policy, extended key usage, authority and subject information access, TLS features and OCSP no-check. Use RFC 5280, RFC 7633 and RFC 6960 for their respective extension grammars and defaults, applied to the supplied extension contents. Also retain Entrust version information, Netscape certificate type, signed certificate timestamp-list bytes and Microsoft enrollment certificate-type text. Unknown extensions retain their numeric identity and encoded value. Distinguish critical from noncritical extensions and absent extensions from present values; omitted extension criticality means noncritical.

- Expose whether basic constraints declare a certification authority and its supplied maximum path length; without a certification-authority declaration, expose no maximum path length. For issuer and subject names with no repeated attribute identity within a relative distinguished name, classify a certificate as a possible self-signature only when the names are equal and any simultaneously present subject and authority key identifiers agree; otherwise classify it as not a self-signature candidate.

- Extract complete and delta CRL distribution points separately, retaining full-name points containing URI alternatives and excluding relative-name points. Extract OCSP access locations only from OCSP entries containing HTTP, HTTPS, LDAP or LDAPS URIs.

- For a document unchanged since its first digest request, compute certificate SHA-1 and SHA-256 digests under FIPS PUB 180-4 over the serialized complete certificate, including its signature. Make each digest available as binary digest data and as a human-readable fingerprint.

- Read and create OpenSSL trusted-certificate documents that append auxiliary trust information to a certificate. Preserve trusted and rejected purposes, alias, key identifier and auxiliary algorithm descriptions separately from the certificate.

- Within subject directory attributes, retain supplied supported-algorithm declarations with optional intended key usage and certificate-policy identifiers. Interpret date of birth, place of birth, gender, country of citizenship and country of residence under RFC 3739 using their supplied values. Unknown subject directory attributes retain their identities and open values.

- Read and create TPM specification attributes containing supplied family, level and revision, TCG platform specification attributes containing supplied major and minor versions, revision and platform class, and TPM security-assertion attributes. Security assertions preserve the supplied generation method and location, certificate-generation location, Common Criteria information, FIPS information and ISO 9000 information. Generation methods distinguish internal, injected, internally revocable and injected revocable; generation and certificate-generation locations distinguish the TPM manufacturer, platform manufacturer and endorsement-certificate signer. Common Criteria information retains the supplied version, assurance level from one through seven, evaluation status of designed to meet, evaluation in progress or evaluation completed, optional strength of basic, medium or high, and optional profile and target identities and references. FIPS information retains the supplied version and security level from one through four. References retain supplied URIs, digest descriptions and digest bits. Omitted security-assertion version means version one; omitted field-upgrade, ISO 9000 certification and Common Criteria or FIPS plus flags mean false.

### FP-10: Certificate DNS and IP identity matching

- Determine certificate DNS identities from DNS subject alternative names, eliminating duplicate DNS entries. When a nonempty subject alternative-name extension is present, do not use common names as DNS identities, even if that extension contains no DNS entries. Otherwise accept common names consisting of at least two dot-separated DNS labels with alphanumeric ends and optional interior hyphens, an alphabetic final label of at least two characters, and an optional entire leftmost wildcard label.

- Match a supplied DNS name against those identities without regard to letter case, treating Unicode and IDNA forms as equivalent under RFC 3490. Require equal label counts and exact agreement in every label after the first. Permit exactly one wildcard in the first certificate label, including a wildcard embedded in that label, but prohibit wildcard matching when that certificate label begins with the IDNA ASCII prefix. A wildcard matches zero or more characters only within the first label. Return a nonmatch when no identity satisfies these rules.

- Obtain certificate IP identities only from IP subject alternative names. Match supplied valid IPv4 and IPv6 addresses by their binary address values, so equivalent IPv6 spellings match. Return a nonmatch when no IP identity agrees, and refuse a non-text matching request as an input-type error.

### FP-11: Certificate revocation lists

- Read, create and modify version-one and version-two X.509 CRL structures under RFC 5280 from supplied fields and signature bytes. Expose issuer, signature algorithm, signature, update times and all revoked entries, retaining each entry's serial number and revocation date in document order. Preserve an omitted version, next-update time and revoked-entry collection as absent.

- Interpret CRL extensions for issuer alternative name, CRL number, delta CRL indicator, issuing distribution point, authority key identifier, freshest CRL and authority information access, and entry extensions for reason, hold instruction, invalidity date and certificate issuer, using RFC 5280 and the supplied extension values. Distinguish critical extensions and absent values, treat omitted extension criticality as noncritical, and retain unrecognized extension contents. Reason values distinguish unspecified, key compromise, CA compromise, affiliation changed, superseded, cessation of operation, certificate hold, removal from CRL, privilege withdrawn and authority-attribute compromise.

- Extract HTTP issuer-certificate locations from authority information access, excluding other access methods and URI schemes. Extract full-name delta CRL distribution points containing URI alternatives, excluding relative-name points.

- For a document unchanged since its first digest request, compute SHA-1 and SHA-256 CRL digests under FIPS PUB 180-4 over the serialized complete CRL, including its signature.

- For an entry carrying a certificate-issuer extension, expose the first directory-name alternative as its issuer; if the extension has no directory-name alternative, expose no issuer. For an entry without that extension, expose its issuer as unspecified by the entry.

### FP-12: Certificate signing requests

- Read, create and modify PKCS#10 certificate signing requests under RFC 2986, preserving the supplied version, subject name, subject public key, attributes, signature algorithm and signature bytes. Distinguish an omitted attribute collection from an explicitly empty collection.

- Interpret challenge-password, extended-certificate-attribute and requested-extension attributes under RFC 2985 using the supplied attribute contents. Requested extensions retain their identities, criticality and values, including subject alternative names. Preserve unknown request attributes as identified open ASN.1 values.

- Read and create Microsoft enrollment provider, operating-system version and request-client-information attributes, preserving supplied provider identity, key specification, signature bits, client identity, machine, user and process information.

### FP-13: OCSP request and response documents

- Read, create and modify OCSP requests under RFC 6960 from supplied certificate identifiers, requestor information, optional signature and extensions. Preserve every requested certificate's hash algorithm, issuer-name hash, issuer-key hash and serial number, and distinguish unsigned requests from requests carrying a signature and certificates. An omitted request version identifies version one.

- Read, create and modify OCSP responses under RFC 6960, distinguishing successful, malformed-request, internal-error, try-later, signature-required and unauthorized statuses. For a supplied basic response, expose responder identity, production time, individual certificate responses, signature and included certificates. Distinguish good, unknown and revoked certificate statuses; revoked status exposes the supplied revocation time and optional reason. Preserve each response's update times and optional next-update time. An omitted basic-response version identifies version one.

- Interpret OCSP request-wide extensions for nonce, acceptable responses and preferred signature algorithms, per-request service-locator extensions, response-wide nonce and extended-revocation extensions, and single-response CRL reference, archive cutoff, reason, invalidity date and certificate issuer extensions under RFC 6960 and RFC 5280. Preserve signed certificate timestamp-list payloads as bytes. Expose extension criticality, treat omitted criticality as noncritical, distinguish absent extension values and retain unrecognized extension contents.

### FP-14: CMS and PKCS#7 message documents

- Read, create and modify CMS content under RFC 5652 and PKCS#7 content under RFC 2315. Support data, signed data, enveloped data, signed-and-enveloped data, digested data, encrypted data, authenticated data, compressed data under RFC 3274 and authenticated-enveloped data under RFC 5083. Interpret the content according to its supplied content identity, preserving the appropriate encapsulation for CMS and PKCS#7 and distinguishing detached content from present content.

- For signed content, expose supplied digest descriptions, signer identities, signatures, signed and unsigned attributes, certificates and revocation information. For encrypted and enveloped content, retain encrypted bytes and algorithm parameters and distinguish key-transport, key-agreement, key-encryption-key, password and other recipient information. For authenticated and digested content, preserve the supplied authentication or digest values and their algorithm descriptions.

- Interpret CMS attributes for content type, message digest, signing time, countersignature, S/MIME capabilities, encryption-key preference, signature timestamp token, algorithm protection, Microsoft nested signature and Microsoft timestamp token. Use RFC 5652, RFC 2633, RFC 3161 and RFC 6211 for the respective standard-defined attribute grammars, with the caller's supplied values; preserve Microsoft attributes as embedded CMS content. Retain unknown attribute identities and their open values.

- Preserve CMS certificate choices for X.509, extended, version-one attribute, version-two attribute and other certificate formats, with version-one attribute certificate support limited to reading supplied encodings that explicitly carry their version. Preserve revocation choices for CRLs and other revocation formats, including supplied OCSP responses and SCVP request-and-response content under RFC 5055. For attribute certificates, expose holder or subject as applicable, issuer, validity, signature and supplied attributes; interpret authentication information, access identity, charging identity, group, role and clearance attributes under RFC 5755. Retain supplied timing metrics for NTP time, offset, delay, expiration and leap events, and timing-policy identifiers with optional maximum offset and delay, as structured values.

- For compressed content carrying the zlib compression identity, return the original content after decompression under RFC 1950 and RFC 1951, using the encapsulated compressed bytes as input. Refuse corrupt compressed content as invalid compressed data.

### FP-15: PKCS#12 key and certificate containers

- Read, create and modify PKCS#12 PFX containers under RFC 7292, preserving the supplied version, authenticated content, optional MAC description, salt and iteration count. An omitted MAC iteration count means one. For an authenticated safe carried as data, expose its ordered content entries and distinguish plain content from encrypted content while retaining the supplied ciphertext and encryption parameters.

- Read and create safe contents containing private-key bags, encrypted-private-key bags, certificate bags, CRL bags, secret bags and nested safe contents under RFC 7292. Select the supplied bag's interpretation from its identity, preserve nested bag contents and expose X.509 certificates embedded in certificate bags. Certificate bags also retain SDSI certificate identities and their supplied payload bytes. Retain CRL and secret bag payloads without changing their bytes.

- Preserve bag attributes for friendly names, local key identifiers, Microsoft local-machine-keyset information and Java trusted key usage. Interpret friendly names as text, local key identifiers as bytes and trusted key usage as purpose identifiers; retain unknown attributes as open ASN.1 values. Distinguish omitted bag attributes from present attributes.

### FP-16: Timestamp requests, tokens and evidence documents

- Read, create and modify TSP requests under RFC 3161 using supplied message-imprint algorithms and digest bytes, policies, nonces, extensions and certificate requests. An omitted certificate request means false. Read, create and modify TSP responses carrying a supplied timestamp token. Independently read and create RFC 3161 status information distinguishing granted, granted-with-modifications, rejected, waiting, revocation-warning and revocation-notification statuses, retaining supplied status text and failure flags.

- Extend CMS content interpretation to expose timestamp tokens carried in signed content as RFC 3161 timestamp information, exposing the supplied policy, message imprint, serial number, generation time, accuracy, ordering, nonce, authority name and extensions. Omitted ordering means false. Extend CMS attribute interpretation to read and create signing-certificate attributes under RFC 2634 and RFC 5035, preserving certificate references, issuer information, policies and selected digest descriptions; the version-two certificate reference uses SHA-256 when its digest description is omitted.

- Read and create timestamped-data documents carrying an optional data URI, optional metadata, optional content and temporal evidence, and interpret them when carried in CMS. Distinguish evidence containing encapsulated timestamp information, archive evidence records and other identified evidence. Timestamp-information entries retain their supplied information and optional CRLs; archive entries retain supplied CMS timestamp tokens, digest descriptions, partial hash trees, attributes and encryption information. Other evidence retains its supplied identity and open value. Preserve archive timestamp entries in their supplied order.

### FP-17: PDF signature validation-material structures

- Extend X.509 extension interpretation to read and create PDF 1.7 Adobe certificate extensions for archival revocation information, timestamp-service information and PPKLite credentials. Preserve supplied versions, timestamp location and authentication requirement; an omitted authentication requirement means false. Recognize the PDF-signing certificate purpose.

- Extend CMS attribute interpretation to read the Adobe revocation-information archival attribute used by PDF 1.7 signatures and create it when at least one revocation collection is supplied, including an explicitly empty collection. Expose supplied CRLs, OCSP responses and other identified revocation payloads as distinct collections, preserve their contents, and distinguish each absent collection from a present collection. Interpret this attribute when carried in CMS signed attributes.
