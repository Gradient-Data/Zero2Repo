# Velnora Full Product Requirements

Velnora provides asynchronous SSHv2 clients and servers for Python applications, including remote sessions, network forwarding, file transfer, and management of SSH identities and trust.

### FP-01: SSH key management

- Callers can generate DSA, RSA, ECDSA, Ed25519, and Ed448 private keys and obtain their corresponding public identities. ECDSA supports NIST P-256, P-384, P-521, and secp256k1. Generated RSA keys default to 2048 bits with public exponent 65537 and accept a caller-selected integer size of at least 1024 bits and public exponent 3 or 65537; DSA generation produces 1024-bit keys. Unsupported key types or generation settings fail as invalid key-generation requests.

- Private keys can be loaded from supplied data or files and exported in OpenSSH and PKCS#8 DER or PEM forms. DSA, RSA, and ECDSA also support their traditional private-key DER and PEM forms. Public and private key exports default to OpenSSH form. Public keys support OpenSSH, RFC 4716, and PKCS#8 DER or PEM forms, with traditional DER and PEM forms for DSA and RSA. Reading an exported key preserves its public identity and, for private keys, its ability to authenticate. A format which cannot represent the selected key type is refused as an unsupported key format.

- Callers can protect private-key exports with a passphrase in OpenSSH, traditional PEM, and PKCS#8 DER or PEM forms and recover the same private identity with the correct passphrase. Callers can select AES-256-CBC protection in each of these encrypted forms. A missing or incorrect required passphrase refuses private-key recovery; this failure need not be distinguished from invalid key material. Malformed key material fails as an invalid key. Public-only material cannot be exported as a private key. Without a passphrase, private-key exports are unencrypted; requesting protection for traditional DER is refused as an unsupported encrypted format.

- Keys without a supplied comment have no comment. Callers can read, change, and clear key comments, read collections of public or private keys from files, and write or append keys without changing their public identities. Comments survive export and import in OpenSSH and RFC 4716 public-key forms and OpenSSH private-key form.

- For DSA, RSA, NIST ECDSA, Ed25519, and Ed448 identities, key fingerprints use a caller-selected MD5, SHA-1, SHA-256, SHA-384, or SHA-512 digest, defaulting to SHA-256, over the SSH public-key representation. For DSA and RSA this representation is defined by RFC 4253, for NIST ECDSA by RFC 5656, and for Ed25519 and Ed448 by RFC 8709; the digest is defined by RFC 1321 for MD5 and FIPS 180-4 for the SHA choices. An unsupported digest choice is refused as an invalid fingerprint request.

- OpenSSH security-key references for ECDSA with NIST P-256 and Ed25519 can be loaded and exported while retaining their public identity and authenticator application. Exporting these references as PKCS#8 private keys is refused as an unsupported key format.

### FP-02: SSH certificates

- A caller with a signing private key can issue OpenSSH version 01 user and host certificates for DSA, RSA, ECDSA, Ed25519, and Ed448 public keys. The resulting certificate retains the subject key, user or host role, caller-selected identity, serial number, principals, and validity interval. OpenSSH certificates default to serial number zero, no principal restriction, and validity from the Unix epoch without an effective expiration; their validity includes the starting time and excludes the ending time. Unsupported certificate versions and an ending validity time at or before the starting time are refused as invalid certificate-generation requests.

- User certificates can carry a forced command, allowed source networks, and permissions for X11 forwarding, agent forwarding, port forwarding, pseudo-terminals, and user startup files. The caller can enable or disable each permission independently; these permissions are enabled by default. Certificates can be imported, exported, read, written, and appended in OpenSSH and RFC 4716 forms without changing their signed meaning.

- Callers can issue X.509 user, host, and certificate-authority certificates for DSA, RSA, ECDSA, Ed25519, and Ed448 keys, with selected subject, issuer, principals, validity, serial number, and extended purposes. Certificate-authority certificates can constrain subordinate authority depth. When the signing and subject keys use different families, callers may need to select a digest compatible with the signing key; automatic digest selection is not guaranteed for cross-family issuance. X.509 certificates can be loaded and exported in DER, PEM, and OpenSSH forms, and certificate chains can be supplied as ordered collections of certificates. Malformed certificates fail as invalid certificate material.

- A caller can associate a certificate with its matching private key, including automatic association when supplying separate collections of keys and certificates. A certificate for a different public key is refused as a key and certificate mismatch.

- X.509 certificate validation checks the supplied chain against selected trust roots, certificate validity, the requested host or user identity, and selected extended purposes. When a certificate constrains its extended purposes, at least one selected purpose must be present. Purpose-restricted validation accepts caller-selected purpose object identifiers. User and host principal checks require an exact match with a certificate principal; when no subject alternative names are present, common names supply those principals. Callers can disable purpose checking. A certificate with no extended-purpose restriction satisfies purpose checking. An expired chain, untrusted chain, mismatched principal, or unsatisfied purpose causes an identity-validation failure.

### FP-03: Host trust and authorized identities

- OpenSSH host-trust data can be loaded from text or files and matched against a supplied host name, address, and port. Matching supports plain names, hashed entries, wildcard inclusions and exclusions, and address networks. A matching exclusion prevents that entry from matching. Port-qualified entries apply only to the specified port; when looking up a nondefault port, unqualified entries are considered if the port-qualified lookup supplies no directly trusted key, trusted authority, trusted X.509 certificate, or trusted X.509 subject pattern.

- Host-trust matching distinguishes directly trusted host keys, trusted certificate-authority keys, and revoked keys. With X.509 identities it also distinguishes trusted and revoked certificates and subject-name patterns. Subject matching supports a complete distinguished name or a prefix of its relative distinguished names. An identity appearing in both trusted and revoked entries remains identifiable as revoked.

- OpenSSH authorized-identity data can authorize a supplied public key or certificate authority and expose the matching entry's restrictions. Source restrictions match the peer host name or address, including networks and exclusions; principal restrictions match certificate principals, including wildcard exclusions. Each source restriction must match, and each principal restriction must match at least one supplied principal when principals are supplied. When several entries authorize the same identity, the first eligible entry supplies its restrictions. X.509 authorization can select a certificate by its public key and subject or by a complete or prefix subject-name pattern, subject to the entry's source and principal restrictions. A key which has no eligible entry is not authorized.

- Authorized identities can restrict pseudo-terminals, X11 forwarding, agent forwarding, and port forwarding, limit permitted forwarding destinations, and supply a forced command and environment values. At the identity-authorization level, pseudo-terminal, X11, agent-forwarding, and port-forwarding permissions are granted unless their disabling restrictions are present. A permitted forwarding destination can specify a numeric port or a wildcard accepting any port at that host. Malformed option syntax, environment assignments without a variable name, and forwarding destinations without a valid port specification are refused as invalid authorization data.

### FP-04: OpenSSH configuration

- Callers can supply OpenSSH client or server configuration files as connection defaults. Explicit connection choices override file-provided defaults. The first applicable value wins, including for a list-valued setting, except that client identity files, client certificate files, names of environment variables to send, server host keys, and server host certificates accumulate across applicable entries. Unsupported configuration directives are ignored. Noninteger values for integer settings, unrecognized choices for boolean-only settings, address families, terminal-request modes or canonicalization modes, missing required values, and unbalanced quoting fail as invalid configuration with the offending file and line identifiable.

- Client configuration controls address family, bind address, destination name and port, user identity, host-key aliases and trust sources, client keys and certificates, agent selection and identity filtering, PKCS#11 provider selection, authentication methods and preference, GSSAPI delegation, host-based signing, key exchange, encryption, integrity protection, authentication signature choices, host-key preferences, compression, connection timeout, keepalives, rekey limits, proxy commands, jump hosts, default remote command, pseudo-terminal requests, session environment, agent forwarding, optional X11 setup, hostname canonicalization, TCP keepalives, and connection tags. Server configuration controls address family and port, host keys and certificates, authorized-key sources, authentication methods, GSSAPI key exchange, advertised authentication signature choices, key exchange, encryption, integrity protection, compression, login timeout, keepalives, rekey limits, agent forwarding, pseudo-terminals, peer-name lookup, TCP keepalives, and hostname canonicalization.

- Client host blocks apply settings only to matching original host names. Host and identity patterns support zero-or-more-character wildcards, single-character wildcards, and exclusions; an exclusion overrides an inclusion in the same pattern list. Conditional blocks can combine and negate supported conditions. Client conditions cover all connections, successful hostname canonicalization, command exit success, destination host, original host, local user, remote user, connection tag, and membership of a local interface address in a supplied network. Server conditions cover all connections, successful hostname canonicalization, command exit success, peer host, peer address, local address, local port, and user. Every condition in a block must hold after its own negation for that block to apply. Final-only blocks contribute to the resulting connection configuration even without hostname canonicalization, while retaining earlier applicable values. Unsupported condition names are refused as invalid configuration.

- Included configuration files contribute settings as if read at the inclusion point; include patterns with no matching files contribute no settings. Client identity-file, certificate-file, agent-location, proxy-command, and remote-command values can substitute the destination host, original host, destination port, remote user, local user, local home directory, local user id, full or short local host name, and environment-variable values. The destination-name setting can substitute the original destination host. Server authorized-key locations can substitute the authenticated user and environment-variable values. A referenced environment variable or substitution token which cannot be resolved fails as invalid configuration.

- For server authorized-key location substitution, a user name is unsafe if it is exactly the parent-directory name, starts with a home-directory marker or a drive-letter prefix, contains a path separator, or contains an environment-variable substitution. Such a name is refused as an unsafe user identity rather than being used to select an authorized-key location.

### FP-05: SSH agent and token identities

- Callers can connect to a local OpenSSH ssh-agent, enumerate its available public identities and comments, and use those identities for signing without supplying the private-key material. The caller can select the agent explicitly or use the agent advertised by the local environment. A missing agent location or an inaccessible agent fails as an unavailable agent.

- Callers can add private identities and associated certificates to an agent, enumerate the updated identities, remove selected identities, and remove all identities. Agent-supported lifetime and confirmation restrictions remain effective when requested. Refused modifications or signing requests fail as agent operation failures.

- An agent can be locked with a caller-supplied passphrase and unlocked with that passphrase. While locked, its protected identities are unavailable for signing; an incorrect unlock passphrase leaves it locked and is reported as an agent operation failure.

- Through a caller-selected locally available PKCS#11 provider, callers can load RSA and ECDSA signing identities and associated X.509 certificates, select tokens by label or serial number, and select keys by label. Only identities satisfying all supplied label and token selectors are returned. A token requiring a PIN must receive an accepted PIN for protected access; unavailable providers or refused token access fail as identity-access failures.

### FP-06: Secure SSH connections

- Applications can initiate and accept SSHv2 connections over TCP, or start the client or server role on an already connected socket. The default destination or listening TCP port is 22. SSH transport interoperates according to RFC 4253 using the peers' identification, key-exchange offers, host identity, and exchanged key material. An incompatible protocol version, an unexpected transport message type, or a failed integrity check terminates the affected connection as a protocol, negotiation, or integrity failure rather than delivering the affected payload.

- With host verification enabled, a client accepts only a server identity approved by supplied trust material or the caller's validation policy. Its default trust source is the local user's host-trust data. Unknown, changed, or revoked host keys fail as unverifiable host identities. OpenSSH host certificates additionally require the correct host role, a trusted signing authority, current validity, and a matching host principal when principals are restricted. Host-key aliases allow a caller to reach a network destination while using the supplied alias for host-trust lookup and host-certificate principal validation. A caller can explicitly disable host verification.

- Callers can select ordered allowable key-exchange, encryption, integrity, and compression choices, and can restrict allowable signatures. Transport negotiation follows RFC 4253 section 7.1 for the peers’ ordered offers. A signature selection restricts the available algorithms. Unsupported explicit algorithm choices fail as invalid configuration, and incompatible peer offers fail as negotiation failures. Algorithm selection supports wildcard matching and replacement, prepending, appending, or removal relative to the default selection.

- Software key exchange supports Curve25519, Curve448, ECDH with NIST P-256, P-384, P-521 and secp256k1, fixed-group Diffie-Hellman, group-exchange Diffie-Hellman, RSA key exchange, and hybrid ML-KEM. Fixed-group combinations are group 1 with SHA-1; group 14 with SHA-1, SHA-224, or SHA-256; group 15 with SHA-256, SHA-384, or SHA-512; group 16 with SHA-384 or SHA-512; and groups 17 and 18 with SHA-512. Group exchange supports SHA-1, SHA-224, SHA-256, SHA-384, and SHA-512. RSA key exchange supports 1024-bit RSA with SHA-1 and 2048-bit RSA with SHA-256. Hybrid choices are ML-KEM-768 with X25519 or NIST P-256 and ML-KEM-1024 with NIST P-384. GSSAPI key exchange supports Curve25519 with SHA-256, Curve448 with SHA-512, NIST P-256 and secp256k1 with SHA-256, NIST P-384 with SHA-384 and P-521 with SHA-512, group exchange with SHA-1 or SHA-256, group 1 with SHA-1, group 14 with SHA-1 or SHA-256, and groups 15 through 18 with SHA-512. With SNTRUP available, SNTRUP761 with X25519 is also supported. The default non-GSS selection permits Curve25519, Curve448, all listed ECDH curves, group 14 with SHA-1 or SHA-256, groups 15 through 18 with SHA-512, group exchange with SHA-256, RSA with SHA-256, and the available listed hybrid choices. The default GSSAPI selection permits its listed choices except group 1 and group exchange with SHA-1. Other listed key-exchange choices require explicit enablement.

- Encryption choices are ChaCha20-Poly1305, AES-GCM with 128- or 256-bit keys, AES-CTR and AES-CBC with 128-, 192-, or 256-bit keys, Triple DES-CBC, Blowfish-CBC, CAST128-CBC, SEED-CBC, and RC4 with 128- and 256-bit keys. By default only ChaCha20-Poly1305, AES-GCM, and AES-CTR are enabled. Other choices require explicit enablement.

- Integrity choices include HMAC with SHA-1, SHA-224, SHA-256, SHA-384, SHA-512, and MD5, plus 96-bit truncated HMAC with SHA-1, SHA-256, SHA-512, and MD5. Encrypt-then-MAC is supported with HMAC-SHA-1, HMAC-SHA-256, HMAC-SHA-512, and HMAC-MD5, including their 96-bit truncated forms. With UMAC available, 64- and 128-bit UMAC are supported with or without Encrypt-then-MAC. MD5 and truncated HMAC choices are disabled by default.

- Compression can be disabled or use zlib compression, either throughout the connection or only after successful authentication. By default the client prefers no compression and the server permits delayed compression or no compression; compression before authentication requires explicit enablement. Enabling compression through a configuration file prefers delayed compression, then compression throughout the connection, then no compression; disabling it prefers no compression, then delayed compression, then compression throughout the connection.

- Host and user signatures support RSA with SHA-1, SHA-224, SHA-256, SHA-384, or SHA-512, ECDSA on the supported curves, Ed25519, Ed448, and DSA. DSA signatures require explicit enablement. OpenSSH certificates and X.509 certificates can supply host and user identities as alternatives to bare keys.

- Callers can discover a server's presented host key without opening an application session. A configured host-key update observer distinguishes host keys newly offered, removed, retained, or revoked by the server; additional keys are accepted as proved only when the server demonstrates possession of their private keys.

- Multiple connections can remain active in the same application, and closing one does not close unrelated connections. Callers can close gracefully, abort, or request disconnection and await observable closure. Connection closure closes its associated channels and listeners; transport loss is distinguishable from successful completion of an operation which required further peer data.

- A caller-selected connection deadline bounds establishment including TCP connection, SSH negotiation, and authentication, with expiration reported as a connection timeout. This additional deadline is disabled by default, and zero also disables it. A negative deadline is refused as an invalid connection setting.

- Callers can request rekeying after a selected amount of outgoing traffic or elapsed time while retaining an established connection's channels and their data. Defaults are one hour or a total of 1 GiB in the outgoing packet-length values defined by RFC 4253 since the previous key exchange; the next outgoing packet after either threshold is reached causes renewed key exchange. A zero time interval disables time-based rekeying. Nonpositive traffic thresholds and negative time intervals are refused as invalid settings. With keepalives enabled, a peer which remains unresponsive beyond the caller-selected unanswered-request allowance is disconnected as an unresponsive connection. Keepalives are disabled by default; the default allowance when enabled is three unanswered requests. Negative keepalive intervals or allowances are refused as invalid settings. An initial unanswered-request allowance must be positive. On an existing connection, changing it to zero closes the connection at the next keepalive interval without waiting for a reply exchange.

- Caller-supplied time intervals can use seconds, minutes, hours, days, or weeks, alone or combined by addition; a day is 24 hours and a week is seven days. Numeric intervals without a unit mean seconds. Byte counts can use bytes or binary multiples of 1024, 1024 squared, or 1024 cubed. Unrecognized units and malformed quantities fail as invalid settings.

### FP-07: Client authentication and access policy

- After secure transport is available, SSH application access requires successful authentication unless the server explicitly permits access without credentials. Supported authentication methods are public key, host based, password, keyboard interactive, GSSAPI with key exchange, and GSSAPI with message integrity. GSSAPI use requires valid local credentials and a reachable local authentication realm. Callers can enable or disable methods and select their preference order; the default preference is GSSAPI with key exchange, GSSAPI with message integrity, host based, public key, keyboard interactive, then password; exhausted or disallowed credentials fail as denied authentication.

- Public-key authentication succeeds only when the server accepts the user identity and key and the client proves possession of the matching private key. Clients can use supplied keys, local default identities, OpenSSH or X.509 certificates, and selected ssh-agent identities. Identity filtering excludes agent keys outside the caller's selected identities. The default remote user is the local user. Server-advertised authentication methods can be obtained without opening an application session.

- For OpenSSH user certificates authenticated through an authorized certificate authority, acceptance requires a valid signature, user role, current validity interval, an authorized principal, and satisfaction of source-address restrictions. Unknown critical restrictions, an untrusted authority, and failed restrictions cause denied authentication. With no explicit principal restriction in authorization policy, a restricted certificate must include the requested user among its principals.

- Password authentication presents caller-provided credentials for server validation. When the server requires a password change, the client can obtain and submit a replacement and distinguish an accepted change from a rejected change. Keyboard-interactive authentication presents each server challenge with its prompt and echo requirements, accepts a corresponding set of responses, and supports multiple challenge rounds.

- Host-based authentication checks the client's host identity, its proof of private-key possession, and the permitted relationship between the remote user and the client-side user. Clients can use OpenSSH ssh-keysign for permitted host identities. GSSAPI authentication can use a locally configured principal and credential store, and credentials are delegated to the server only when the client enables delegation.

- Authentication carries the server's supplied banner to the client. A configured authentication deadline ends an incomplete login as an authentication timeout; the default is 120 seconds after the underlying connection is established, and zero disables this deadline. Negative authentication deadlines are refused as invalid settings. A client which explicitly forbids authentication without a nontrivial credential exchange refuses access offered without that exchange.

### FP-08: Multiplexed channel data and streams

- An authenticated connection supports multiple simultaneous channels whose data and completion remain associated with the channel that produced them. Closing one channel leaves other open channels usable. A rejected channel request is reported as a channel-open failure without requiring closure of the authenticated connection.

- Channels provide ordered bidirectional binary data and optional text conversion using a caller-selected encoding. Text decoding preserves characters whose encoded bytes arrive in separate deliveries. Invalid text under strict conversion fails as invalid encoded data; callers can explicitly select replacement or omission of invalid sequences. Session channels default to UTF-8 text, while network-forwarding channels default to binary data.

- Channel readers support reading available data, complete lines, an exact requested amount, or data through a selected delimiter, and consuming successive received pieces. A delimiter can be a fixed sequence, one of several sequences, or a regular-expression match; the match beginning earliest in the received input ends the read, which includes that delimiter and leaves subsequent data for later reads. Literal delimiter collections with overlapping or prefix-related alternatives are outside this promise. Regular-expression reads cover nonempty, unambiguous delimiter matches; the caller supplies an upper bound on the delimiter length when matching across separate deliveries. An empty delimiter choice is refused as invalid input. End of input before an exact amount or delimiter is obtained is distinguishable from a complete read and retains the partial data. A line read returns a final unterminated line at end of input, and an empty result when no data remains.

- Callers can suspend and resume channel input and wait for pending output to be accepted for onward delivery. Pausing input and later resuming it does not change the delivered data. End of output can be sent independently of receiving further input on channels supporting half-close. Waiting for pending output on a closed or lost channel exposes the channel failure when that output cannot be sent. Acceptance for onward delivery does not promise consumption by the remote application.

### FP-09: Remote sessions and terminal controls

- Clients can request an interactive shell, execution of a supplied command, or a named subsystem, and servers can accept and handle each request or refuse it as an unavailable session. With no command or subsystem selected, the requested activity is a shell. A server with no session handler rejects ordinary session requests.

- Clients can supply session environment values directly and select local environment variables by wildcard name. A directly supplied value wins when both sources name the same variable. The server-side session receives the accepted environment. An authenticated identity's forced command replaces the requested shell, command, or subsystem; a certificate's forced command takes precedence over an authorized-key forced command. Authorized-key environment values supply session defaults, and client-supplied values override them for the same names.

- Clients can request a pseudo-terminal with terminal type, character and optional pixel dimensions, and POSIX terminal modes defined by RFC 4254 section 8 for the supplied mode values. Terminal requests can be disabled, forced, requested whenever a terminal type is supplied, or limited to shells with a supplied terminal type. The default requests a pseudo-terminal when a terminal type is supplied. A terminal refused by server policy or identity restrictions fails as a refused terminal request.

- During a session, client changes to terminal dimensions and requests for a break or named signal are observable by the server-side application. Servers can send ordinary completion with a selected exit status or termination by a selected signal; the client distinguishes those outcomes. Session data retains the distinction between ordinary output and error output when the server sends them separately.

- Server applications can inspect the authenticated user, requested command or subsystem, environment, terminal information, and identity permissions associated with a session.

### FP-10: Remote process execution and redirection

- A caller can run a remote shell, command, or subsystem to completion with supplied input and obtain its ordinary output, error output, and termination outcome. Ordinary nonzero exits are returned as results by default. When successful completion is required explicitly, nonzero exit status or signal termination fails as unsuccessful process execution while retaining the process output and termination information.

- A caller can start a remote process, exchange input and output while it is running, close its input, and await completion. Process termination can be requested by a named signal or by termination and forced termination, corresponding respectively to the POSIX terminate and kill signals. A caller-selected completion deadline expiring before completion fails as a process timeout and retains output collected so far.

- On both client and server, process input and output can be redirected to files, open file-like streams, pipes, sockets, or other remote process streams. Callers can discard output, provide empty input, and merge error output into ordinary output. Redirection transfers the selected data to the selected destination and preserves end-of-input behavior. A caller can replace a redirection on a running process so that subsequent data uses the new destination.

- Remote process interaction is available through asynchronous streams and through the application's asynchronous subprocess interface, with independently observable input, ordinary output, error output, and process completion. Redirecting between remote processes can span different SSH connections.

### FP-11: Interactive server line editing

- Server sessions with a requested terminal type and text encoding provide line editing and input echo by default. Edited input reaches the application as completed lines. In line input, line feed submits the line; Control-B and Control-F move the cursor one character backward and forward; Control-A and Control-E move to the start and end; Control-H deletes the preceding character; Control-D deletes the character at the cursor in a nonempty line; Control-U erases the whole line; Control-K erases from the cursor to the end; Control-Y restores the most recently erased text; and Control-P and Control-N select the previous and next history entries.

- Applications can disable line editing, switch between complete-line and character input, and enable or disable echo. With echo disabled, entered text is delivered to the application without being echoed to the client or added to recallable history. Changing to character input delivers pending line input and allows subsequent characters to reach the application without waiting for a line ending. Returning to complete-line input is supported when the switch to character input delivered no pending line, or after the application explicitly replaces the pending input and resets its cursor position.

- The default maximum pending line is 1024 characters; additional inserted characters are not accepted once that length is reached. The caller can choose a different maximum or zero for no line-length limit. History retains at most the selected number of nonempty echoed lines, defaulting to the most recent 1000; a nonpositive history size disables history.

- Applications can clear or replace the pending input and cursor position, and register or remove custom key actions which transform pending input, accept or reject a key, or deliver a signal. Editor output accommodates terminal-width changes and characters occupying multiple display columns so that cursor movement and deletion operate on the intended input characters.

### FP-12: TCP and UNIX domain forwarding

- An authenticated client can request direct connections to remote TCP destinations or UNIX domain sockets and exchange bidirectional data. Servers can forward to the requested destination or handle the connection's data in the application. The requested destination and origin information are available for the server's acceptance policy. Refused destinations and failed destination connections are reported as channel-open failures.

- Callers can establish local or remote listeners which forward accepted connections across SSH to a selected TCP destination or UNIX domain socket. Forwarding supports TCP to TCP, UNIX socket to UNIX socket, and both mixed directions. Requesting an automatically allocated TCP listening port exposes the actual allocated port. An unavailable bind address or occupied port fails as inability to open the listener; a server's refusal of a remote listener is distinguishable from successful listener creation.

- Servers can permit or reject remote listening and direct connection requests according to destination and origin. Callers handling remote accepted connections can select the forwarding destination or reject individual connections. Identity restrictions on forwarding and permitted destinations override a general forwarding permission.

- Closing a forwarding listener prevents new connections through that listener while leaving its established forwarded connections usable.

### FP-13: Dynamic SOCKS forwarding

- A local dynamic listener accepts SOCKS version 4, version 4a, and version 5 connection requests and forwards each accepted TCP destination over SSH. SOCKS 4 supports IPv4, SOCKS 4a supports destination host names, and SOCKS 5 supports IPv4, IPv6, and host names. SOCKS 5 supports unauthenticated negotiation.

- Dynamic forwarding supports connection requests only. An unsupported SOCKS version, command, address type, malformed request, or SOCKS 5 offer without unauthenticated access does not open a destination connection. Failed or prohibited destinations leave no usable forwarded data connection.

### FP-14: SSH connection topologies

- A client can establish another independently authenticated SSH connection through an existing SSH connection or a caller-selected sequence of jump hosts. The target connection uses its own target identity, host verification, and credentials, and carries sessions to the target. Failure of a required hop or target authentication fails the requested connection.

- Applications can run SSH over a caller-selected proxy command's bidirectional input and output. Failure to start the proxy or loss of its connection is exposed as a connection failure.

- Reverse-direction connections allow the TCP initiator to act as the SSH server and the TCP listener to act as the SSH client. These roles can also operate through SSH tunnels. Host verification, authentication, and application-session direction follow the SSH roles rather than which side initiated TCP.

- Optional hostname canonicalization searches the caller's domain suffixes for eligible host names, and follows aliases only when both the expanded name and alias match a permitted alias rule. By default canonicalization is disabled; when enabled it applies to names with at most one dot. Canonicalization also applies when a proxy command carries the connection. Callers can change the dot threshold. If canonicalization finds no name, ordinary local name resolution is used by default; callers can instead require a name-resolution failure.

### FP-15: SSH agent forwarding

- When a client requests agent forwarding and the server permits it, applications in the remote session can access the selected client ssh-agent through a local UNIX domain socket or through the server's agent access capability. Agent identity enumeration and signing requests reach that agent and return its results. Forwarding is not requested by clients by default.

- A server or authenticated identity which prohibits agent forwarding does not expose forwarded agent access to the session. An unsolicited agent channel without enabled forwarding is refused. Failure to reach the selected agent is exposed as failed agent access rather than a successful signature.

### FP-16: X11 forwarding

- A session can request X11 forwarding to a caller-selected local display or the display selected by its local environment. When both peers permit forwarding and valid local display authorization is available, remote X11 connections reach that display and exchange bidirectional X11 traffic. The remote session obtains the forwarded display identity, retaining the selected screen number, and usable authorization information. X11 forwarding is disabled by default.

- Forwarding admits X11 connections only when their presented authorization matches the forwarding authorization for that session; mismatches do not reach the local display. Callers can limit a forwarding request to a single X11 connection.

- A missing or invalid display specification, malformed local authorization data, prohibited forwarding request, or unavailable forwarding listener causes a required X11 setup to fail as an inability to enable X11 forwarding. A caller can explicitly request optional X11 setup, in which case the ordinary SSH session can proceed without X11 forwarding when setup fails.

### FP-17: TUN and TAP packet channels

- Clients can request layer 3 TUN or layer 2 TAP packet channels with a selected remote interface number or automatic selection. Server applications can inspect the requested selection and accept a channel to process its packets directly. Bidirectional packet exchange preserves contents and packet boundaries; TUN channels carry IPv4 and IPv6 packets and TAP channels carry Ethernet frames.

- Servers reject packet channel requests by default and can refuse individual requests as channel-open failures. A tunnel mode other than layer 2 or layer 3 is refused as an unsupported tunnel mode.

### FP-18: SFTP file access and transfer

- Authenticated peers can act as an SFTP client and server and perform file operations against the server's real filesystem or application-supplied file service. The default protocol version is 3; callers can request experimental versions 4, 5, or 6, and peers agree on a version both permit. A server without an enabled SFTP service rejects an SFTP session as an unavailable subsystem. An unusable version exchange fails as an SFTP negotiation failure.

- Clients can open files for reading, writing, creation, exclusive creation, appending, and truncation, and perform reads and writes at selected offsets. Sequential access advances the current file position; seeking can be relative to the start, current position, or end. Exclusive creation refuses an existing destination as a file-operation failure in protocol version 3 and as an existing-file conflict in versions 4 through 6. Reads beyond the end report end of file, and sparse or offset writes retain the same logical contents as the requested writes. File access supports binary data and caller-selected text encodings, defaulting to UTF-8 text.

- Clients can retrieve and change file size, permissions, and access and modification times on paths and open files, and inspect ownership. Ownership-setting requests are limited to those permitted to an unprivileged filesystem owner; reassignment to another user is not supported, and a refused request is reported as a file-operation failure. File inspection can follow a symbolic link or inspect the link itself. Filesystem-space inspection, hard-link creation, replacement rename, file synchronization, and operations on symbolic-link metadata are supported when the peer advertises the needed extension and the filesystem supports the operation. A required unavailable operation fails as unsupported rather than being reported as completed.

- Clients can list directory entries with their attributes, create directories and missing parents, remove empty directories, recursively remove directory trees, remove files, rename paths, create and read symbolic links, obtain canonical paths, and maintain a remote working directory used for relative paths. Removing a symbolic link during recursive removal removes the link rather than its target. A plain rename refuses an existing destination unless replacement is explicitly requested and supported.

- Directory and file searches support wildcard characters, single-character wildcards, character classes, and recursive directory matching. Patterns beginning with a dot support matching dot-prefixed names. Unmatched requested patterns fail as no matching file, unless the caller supplies an error handler which accepts that failure.

- SFTP failures distinguish missing files or paths, denied permissions, invalid response types or invalid remote names and paths, unsupported operations, and lost connections. An operation on a closed file or an invalid remote handle fails as unusable file access. Requesting byte-range locking against the default SFTP server fails as unsupported.

- Clients can download, upload, and copy files within a remote filesystem, including multiple selected sources and recursive directory trees. A single destination can name the output file or an existing destination directory; copying into a directory retains each source's base name. Multiple sources require an existing destination directory. A directory source without recursion is refused as a directory transfer requiring recursion. A missing destination selects the current working directory on the destination side.

- Transfer can preserve source permissions and access and modification times. In recursive directory transfers and transfers of a link into an existing directory, symbolic links are copied as links by default; when following links is selected, their target contents are copied instead. Recursive link copying supports directory trees without link cycles. When preservation of symbolic-link metadata is unsupported, the copied link remains available without a promise to preserve that metadata.

- For local downloads which recreate symbolic links inside a destination directory tree without pre-existing links leading outside it, the confinement root is the supplied destination directory, including a directory newly created by recursive transfer, or the local working directory when no destination is supplied. Absolute link targets and relative targets which leave the selected download root are refused as invalid peer data, and the offending link is not created. Relative link targets which stay inside that root remain permitted, including targets using parent-directory references within the tree. A recursively received child name containing a path separator is refused as invalid peer data; current-directory and parent-directory entries are not downloaded as children.

- Callers can observe per-file transfer progress identifying the source and destination, completed byte count, and total file size. Completed counts stay between zero and the file size. Completion reports the full transferred size. Transfer failures abort the operation by default; a caller-supplied error handler can receive a failure and allow remaining files to proceed, while a failure raised by that handler aborts the transfer.

- A caller can require remote-side file copying; that request fails as unsupported if the server does not offer remote copying. For a peer offering remote copying, source and destination offsets and the selected length identify the bytes copied, and the destination contains those bytes. Offsets default to zero, and a zero length copies from the source offset through the end of the source file. Ordinary copying remains usable without requiring the remote-copy extension.

- An SFTP server can expose a virtual root which maps client absolute and relative paths into a selected directory and returns client-visible canonical paths in that namespace. For symbolic links created through the virtual-root service, link-target reporting also uses that namespace. On directory trees without pre-existing symbolic links leading outside that directory, parent-directory traversal remains within the virtual root and newly created links cannot target outside it. Applications can supply their own path mappings and accept or refuse filesystem operations; clients observe the resulting paths, contents, attributes, or failures.

### FP-19: SCP file transfer

- Callers can use SCP to upload files, download files, and copy between two remote systems through the client. Local and remote source selections can be combined for a remote destination, and established SSH connections can be reused. At least one endpoint must be remote; local-to-local copying is refused as an unsupported transfer.

- SCP can copy a single source to a selected output name or copy sources into an existing directory under their base names. Multiple sources require a directory destination. Local source patterns expand to matching files; remote source pattern expansion follows the remote SCP service. Recursive mode copies directory trees, and preservation mode retains permissions and access and modification times. A directory source without recursion is refused as an unsupported directory transfer.

- A server can enable SCP access using its configured file service, allowing clients to exchange files through that service. SCP remains disabled on the server unless explicitly enabled. Unavailable paths, denied operations, malformed transfer requests, and premature connection loss are exposed as transfer failures.

- Received SCP child names must be base names rather than paths and must not name the current or parent directory. Violations are refused as invalid peer data without writing the offending child. Progress observers can distinguish files, completed byte counts, and total file sizes. For each file, completed counts never decrease, stay between zero and the file size, and finish at that size, including for an empty file. A caller can collect transfer failures through an explicit error handler and continue to remaining sources; otherwise a transfer failure aborts the operation.

### FP-20: SSHSIG signing and verification

- Callers can create OpenSSH SSHSIG version 1 signatures over supplied bytes or file contents using a private key and a nonempty namespace, and verify them against the same data and an allowed signer. The signature binds the data, signing identity, and namespace. SHA-256 and SHA-512 are supported, with SHA-512 and the file namespace selected by default. A missing signing key, unsupported hash, or empty namespace is refused as an invalid signing request. X.509 signing identities are not supported.

- Callers can supply a precomputed digest instead of original data; its digest algorithm is the selected SHA-256 or SHA-512 as defined in FIPS 180-4, operating on the original data bytes in their original order. Verification accepts that digest only for a signature of the corresponding original data. A precomputed digest of the wrong length is refused as invalid digest input.

- Allowed-signers data authorizes public keys by principal patterns, with optional namespace patterns and validity intervals. Excluded patterns prevent the corresponding entry from authorizing that principal or namespace, and current time must be within any specified interval, including its beginning and excluding its end. A changed message, invalid signature, unlisted signing key, excluded principal, disallowed namespace, or out-of-period signer yields an unsuccessful verification result.

- When an OpenSSH certificate is trusted through an allowed certificate authority rather than directly authorizing its subject key, verification also requires that certificate's signature, principal restrictions, and validity interval to be satisfied. Signatures with invalid framing, an unsupported signature-format version, undecodable signing identities, or invalid cryptographic signatures yield unsuccessful verification. A signature selecting a digest other than SHA-256 or SHA-512, or an empty namespace, is refused as invalid signature input; malformed allowed-signers option syntax or a supplied nonempty signer document containing no usable entries fails as invalid signer configuration.
